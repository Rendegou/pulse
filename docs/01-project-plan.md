# PULSE 项目落地方案

## 1. 产品和学习的共同目标

做一个让访客看见“这台服务器此刻发生什么”的实时空间：站内连接形成光点，光标和点击成为交互，Host Radar 展示捕获点可见的入站事件，高并发实验让性能变得可观察。当前实现采用已有的 Go、Gorilla WebSocket、原生 JavaScript 和 Canvas 2D。

近期闭环是“两页连接 → 光标平滑同步 → 点击事件同步 → 断线后恢复”，随后推荐进入固定二维博客街区。A/B 阶段不加入账号、数据库、多人房间、主机抓包或 GPU 引擎。AI 可以推进完整功能包，用户只练一个关键点；产品与学习分开验收，不要求独立重写整个闭环才允许继续。

页面上的“真实”要有明确含义：在线数是连接数；heap/sys 是 Go runtime 口径；视觉呼吸和出生动画是表现层，不是新的网络事件。将来加入模拟样本时必须单独标注模式，不能混入真实指标。

## 3. 原型、当前程序、目标产品分开看

### HTML 外壳

当前 `static/index.html` 负责 `canvas#c`、连接状态标签、四个指标容器和脚本加载；行为来自 `static/app.js`，真实状态来自 `/ws`。

阅读 HTML 时做三件事：找到 JS 查询的每个 ID；找出哪些文字只是静态文案；解释为何 HTML 不需要直接持有 Go 的 Session。

### 最早的独立 Demo

已读取并归档原型 HTML，按“节点来源、运动来源、指标来源、网络调用、计时器”逐项对照。原型中的颜色、排版、运动节奏可作为视觉参考；随机人数、假 RTT、虚构主机事件不能直接转成真实产品数据。

具体改进与数据替换路径见 [从原型到产品](06-prototype-to-product.md)，原件保留在 `docs/references/`。

### 近期产品

保留当前界面和单进程结构，先做好输入、状态、绘制、退出。每次变化能由一个用户动作说明，例如“远程鼠标停下后，光点停在最后一个真实坐标”。

## 4. 执行阶段

新的排期以 [AI 协作路线](07-ai-assisted-roadmap.md) 为准，旧 P0–P4 不再作为课程闸门：

1. **已有基础：** L1–L3 已有实现；缺失的链路测试由 AI 随相关功能补入，不要求用户重写所有简单代码。
2. **A 点击互动：** 合并 L4 与必要的 L6 输入保护，交付一次点击、两页各播放一次、有界生命周期。用户只练零值与缺字段反例。
3. **B 可靠连接：** 合并 L5/L6 必要所有权、失败清理、心跳、重连和预算，补自动测试及最小发布检查。用户练一个失败路径。
4. **C 固定博客街区：** 两间房、两篇文章与真实多人指针；先解决世界坐标和相机一致性，不做自由建房。用户练一次坐标转换。
5. **D 内容留下来：** 核对已有博客，先只读导入；允许编辑前落实身份、所有权、存储和冲突。用户练一个权限或冲突测试。

Host Radar 与性能挑战保留专题；Host Radar 在 B 后具备进入条件，但不作为 C 的前置。用户若更想推进原 PULSE，可将 C 换成 L10 的受控真实观测链。对公网发布仍需满足实际验收和明确授权，不能因为计划提速跳过可靠性。

## 5. 最小协议：先保持现有 cursor 命名

当前浏览器发送：

```json
{"type":"cursor","x":0.25,"y":0.75}
```

当前服务端广播（包含自己，客户端跳过自己的回声）：

```json
{"type":"cursor","id":"visitor-example","x":0.25,"y":0.75}
```

已有消息还包括 `welcome {you,sessions}`、`join {session}`、`leave {id}`、`metrics {conns,heap_mb,sys_mb,dropped}`。当前没有协议版本字段；不要在某一端单独加版本并声称已兼容。

下一课 pulse 的拟定契约：客户端发送 `{type:'pulse',clientEventId,x,y}`；服务端校验后生成自己的 `eventId`，广播 `{type:'pulse',eventId,clientEventId,id,x,y}`。坐标必须存在且为 0..1 有限数；身份始终来自当前连接的 Session，不信任客户端提交的用户 ID。

第一版 pulse 不做本地乐观播放，只播放服务端接受后的事件，从而先避免自身重复播放。事件 ID 用于有界去重，旧点击不在重连后补发。若以后改善本地手感，再用 `clientEventId` 对账，单独增加一课。

## 6. 可靠性课程采用的初始预算

以下是 A/B 的资源预算。前端样本双上限、bufferedAmount 策略和服务端 5 秒写超时已经实现，其余服务端预算待实现；全部都不是性能承诺：

- 入站单条消息上限 4 KiB；只接受当前协议定义的文本帧。
- 全站同时连接初始上限 128，升级前做原子名额预留，失败释放；超额拒绝而非无界建立。
- cursor 每连接平均 20 条/秒，允许短时突发 40 条；客户端采样不能替代服务端限频。
- pulse 每连接平均 2 条/秒，短时突发 4 条；超限丢弃并记录计数。
- writer 超时 5 秒；心跳周期初设 15 秒，读超时 45 秒，收到有效 pong 后延长。测试时将时间注入或缩短，不让测试等待几十秒。
- 当前 64 项发送队列先保留；队列满时在第一版可靠实现中关闭慢连接，让它重连取快照，避免静默漏掉 join/leave 后永久失真。关闭在锁外完成。
- 已有：前端每个远程点在追加时裁剪到最近 1 秒且最多 32 个样本。待 A：脉冲效果最多保留 64 个，过期即删；去重缓存也有时间和数量上限。
- 已有：前端 `bufferedAmount` 达到 64 KiB 时不再追加 cursor，保留最新 `pending` 等待下次发送；这只是应用发送策略，不表示浏览器内存具有该硬上限。

若做“只保留最新 cursor”的发送优化，需要独立设计每个 Session 的最新状态槽与可靠事件队列；不能继续用一个满队列对所有类型无差别静默丢弃。

WebSocket 的待发字节可通过 `bufferedAmount` 观察。接口依据：[MDN bufferedAmount](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/bufferedAmount)。

## 7. 暂缓的专题及进入条件

- **AOI / 聚合广播**：当实际扇出成为瓶颈才引入。N 个客户端各以 f Hz 更新时，全量广播约 N²f 次投递/秒（当前包含自己），不是 Nf。
- **Host Radar / Linux Sensor**：先定义来源和授权边界；测试 fixture 与 live 消息明确分离。当前页面写着“无模拟数据”，不在生产默认编造 host_event。
- **二进制协议**：先测序列化/带宽成本，再设计版本、端序、长度和非法帧处理。
- **WebGPU**：Canvas 出现可重复的渲染瓶颈、并且数据层已经能独立测试后再考虑。
- **eBPF / timing wheel**：有规模证据和明确需求后进入独立学习计划，不作为初学阶段的基础设施。

## 8. 发布与仓库事实

现有 `.github/workflows/deploy.yml` 对 `main` push 执行 vet、Linux 构建、上传与远端脚本重启。仓库没有该远端安装脚本的源码，也没有 pulse 服务的 systemd unit；`deploy/caddy.service` 管理的是代理进程。

因此 B 包应补最小发布检查，L9 专题再补完整可核对的部署契约及回滚演练，不假定远端脚本已经具备原子替换、备份和健康探测。任何服务器地址、容量与证书状态都需要运行时重新验证，历史对话不能当作当前证据。
